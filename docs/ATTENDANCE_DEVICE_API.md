# Attendance Device Integration API — Design (not built)

- **Status:** **Design only** (Phase 8 M7; ADR-079, ADR-081 Q6). Nothing in this document is implemented. Building it waits for:
  - an accepted machine-credential path (ADR-028, still Proposed);
  - a real device to test with.
- **Requirement:** ATT-04 (device integration for biometric, RFID or QR terminals; priority *could*).
- **Scope:**
  - staff check-in and check-out punches (the staff daily register, plan §5);
  - optionally, student arrival for the daily register.

  Hostel roll-call devices arrive with Phase 12 on the same API.

## 1. Principles

1. **Devices are machines, not users.** A device never holds a person's session or password. It authenticates with its own credential, under the ADR-028 token path once accepted, and it can do exactly one thing: submit punch events for its own campus.
2. **The same authorization pipeline.** An event is accepted only when all of these hold:
   - the device is registered, active and bound to one tenant, institution and campus;
   - the tenant is entitled to `attendance`;
   - the person referenced belongs to that institution.

   RLS applies exactly as for any tenant write. There is no platform scope.
3. **Idempotent and ordered by device time.** Devices retry, so every event carries the device's own event id. Duplicates are acknowledged and ignored.
4. **Events, not statuses.** A device reports *a punch happened*. The server derives check-in and check-out times and the day's status with the same rules as manual marking. A punch never overwrites a status saved by a person; a conflict is shown to the marker.
5. **No personal data on the wire beyond a reference.** The device sends a person reference: a staff number, or a card or enrolment token that the tenant maps. It never sends names, photos or biometric templates. Biometric templates never leave the device; storing them in the platform is out of scope.

## 2. Device registration (staff UI, `attendance.device.manage` — a future permission code, MFA)

| Field | Notes |
|---|---|
| name, campus | Each device belongs to one campus of one institution |
| kind | `biometric`, `rfid`, `qr` (informational) |
| secret | Generated by the server and shown **once**. Only a hash is stored (like Phase 2 tokens). Rotation creates a new secret and invalidates the old one after a short overlap |
| allowed IPs | Optional list or CIDR. Requests from other addresses are refused |
| timezone | Defaults to the campus timezone. Used to read device-local times |
| active | Deactivation refuses all further events at once |

Every registration, rotation and deactivation is audited.

## 3. The event endpoint (proposed)

```
POST /api/v1/attendance/device-events/
Authorization: <device credential, ADR-028>
Content-Type: application/json

{
  "events": [
    {"event_id": "dev-42-000123", "person": "T-0042", "at": "2027-03-01T07:58:12+06:00",
     "direction": "in"},
    {"event_id": "dev-42-000124", "person": "T-0042", "at": "2027-03-01T14:03:40+06:00",
     "direction": "out"}
  ]
}
```

- **Batch:** at most 500 events per request. The response lists each event as `accepted`, `duplicate` or `rejected` (with a reason code). A rejected event never fails the whole batch.
- **Idempotency:**
  - the key is `(device, event_id)`, enforced by a unique constraint on a `device_event` table;
  - each event is stored as received: device, person reference, time, direction, outcome;
  - events are retained for 90 days.
- **Clock skew:** events more than 5 minutes in the future (server time) are refused. Events older than the edit window are stored but flagged for review; they do not change the register.
- **Rate limit:** per device, for example 60 requests per minute, so a misconfigured terminal cannot flood the tenant.
- **Mapping:**
  - a staff number maps to an active staff profile of the device's institution;
  - for students, a tenant-issued card token maps to an active student;
  - unknown references are `rejected: unknown_person`, and are never created on the fly.

## 4. Deriving the staff register

For each staff member and date:

- the earliest `in` becomes check-in, and the latest `out` becomes check-out;
- the status becomes `present`, or `late` if check-in is after the configured start;
- this applies only while no person has saved that day's record.

Once a person saves the day, device events only update the times shown to the marker.

The derivation runs in the same transaction as the event insert, row-locking the staff record (`select_for_update`), as in M4.

## 5. Security review items (before building)

- Credential storage, rotation and revocation under ADR-028.
- Replay protection: idempotency key plus timestamp window, and optionally signed bodies (HMAC over the body with the device secret).
- Device theft: deactivation, IP allow-list, and anomaly alerts (for example, punches for many people in seconds).
- Privacy: no biometric data in the platform. Person references are tenant-scoped. Event retention is short.
- Isolation tests: one tenant's device can never write another tenant's records, and RLS covers the event table.
